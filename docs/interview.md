# Демонстрация на собеседовании

## Сценарий на 2–3 минуты

1. Откройте вводный экран и покажите, как четыре отказа и успех складываются в сигнал. Кнопка «Начать расследование» сразу открывает рабочий стол.
2. Откройте «Успешный вход после отказов». Назовите группу: один IP и один аккаунт. Сверьте порог, временные отметки и последнюю успешную запись. Откройте эти записи в журнале.
3. Сохраните «Недостаточно данных» с комментарием «Нужно сверить устройство, MFA и действия после входа». Скачайте JSON или Markdown и покажите вывод вместе с записями.
4. Коротко откройте серию `svc-backup`. Объясните, почему подтверждение устаревшего пароля изменит решение, хотя правило сработало корректно.
5. Если осталось время, импортируйте [учебный CSV](../src/demo.csv). Тот же набор даст те же предупреждения и восстановит результат в том же браузере. Покажите в коде функцию `detect` и один тест на границу окна.

## Вопросы для подготовки

| Вопрос | Что стоит уметь объяснить |
| --- | --- |
| Как считается левая граница окна? | Запись ровно в `t − N` минут входит. Для `after` требуется строгое предшествование успешному входу. |
| Почему объединение даёт серию длиннее порога времени? | Каждое срабатывание прошло проверку в своём окне. Общие записи связывают окна в последовательность. |
| Что произойдёт при одинаковых отметках времени? | Номера стабильны после сортировки, а для правила входа после отказов событий в ту же миллисекунду недостаточно для установления порядка. |
| Почему не пересчитывать все окна с нуля? | Два указателя и счётчики сохраняют состояние текущего окна. После сортировки записи добавляются и убираются по одному разу. |
| Какие ошибки даёт отказ от ID события? | Две реальные идентичные записи могут схлопнуться. Стабильный идентификатор источника устранил бы эту неоднозначность. |
| Может ли один IP обозначать разных людей? | Да, например за NAT или VPN. Для вывода нужна сверка с другими журналами. |
| Что хранится после обновления страницы? | Вывод, комментарий, время и технические ключи. Рабочий журнал заново читается из CSV или из встроенной демонстрации. |
| Зачем Worker и почему работает на Pages? | Worker выполняется в браузере отдельно от интерфейса. Pages отдаёт готовые статические файлы. |
| Как убедиться, что отчёт соответствует анализу? | Сверить id, количество и время подтверждающих событий с открытым предупреждением. Сравнить вывод в интерфейсе и в экспорте. |
| Что поможет отличить подозрительный вход от ошибки? | Контекст устройства, MFA, прошлые входы, смена пароля и действия сессии. |

## Вклад и инструменты

Требования, учебную цель, границы первой версии и визуальное направление задал автор проекта. Автор также выбрал статическое размещение и обработку CSV в браузере. Codex помог спроектировать семантику правил, реализовал первую версию, подготовил синтетические данные, тесты, SVG/CSS-графику, документацию и workflow. Для реализации использованы React, TypeScript, Vite, Web Worker, браузерное хранилище и Playwright. ИИ во время анализа журналов не используется.

Перед собеседованием самостоятельно прогоните демо, откройте реализации трёх правил и вручную рассчитайте один пограничный пример. В рассказе указывайте только те проверки и изменения, которые действительно выполнили сами.

## Идеи развития

- Добавить идентификатор источника в следующий вариант схемы, чтобы надёжнее различать одинаковые записи.
- Поддержать второй формат через адаптер в общее ядро с отдельными тестами.
- Добавить конфиг порогов с версией в отчёте и ключе сохранения.
- Рассмотреть Python API для контролируемого локального развёртывания, когда понадобится обработка больших журналов.
